## 1. System Overview

KP WhatsApp Automation is a multi-tenant WhatsApp automation platform. It connects to WhatsApp using the WhatsApp Web protocol (via the **Baileys** library) — no official WhatsApp Business API is required.

Each business owner links their existing WhatsApp number by scanning a QR code. Once connected, the platform intercepts incoming messages and responds automatically using one of three mechanisms:

- **Welcome Greeting** — a fixed message sent to first-time contacts
- **Keyword Auto-Replies** — instant fixed responses triggered by matching keywords
- **AI Assistant** — intelligent replies generated by a configurable AI model

The platform supports multiple concurrent business sessions, each fully isolated with its own WhatsApp connection, AI configuration, conversation history, and contact list.

## 4. Architecture

### High-Level Flow

```
Customer WhatsApp
      │
      ▼
WhatsApp Servers (WebSocket)
      │
      ▼
Baileys Library  ◄──── Session files (./sessions/business_<id>/)
      │
      ▼
WhatsappService.messages.upsert handler
      │
      ├─► Log incoming message to DB
      ├─► Upsert contact record
      │
      ▼
AiService.handleIncomingMessage()
      │
      ├── Is AI paused for this contact?  ──► Stop (human takes over)
      ├── New contact + greeting enabled? ──► Send greeting message
      ├── Keyword rule matched?           ──► Send fixed keyword reply
      └── AI active + prompt + apiKey?   ──► Call AI provider → send reply
                                              │
                               ┌─────────────┴──────────────┐
                               │        AI Providers         │
                               │  OpenAI / Anthropic /       │
                               │  Gemini / DeepSeek /        │
                               │  OpenRouter                 │
                               └────────────────────────────┘
```

### Multi-Tenant Isolation

Each business is identified by a `businessId` (UUID). All data — sessions, AI configs, message logs, and contacts — are scoped to this ID. The `WhatsappService` maintains an in-memory `Map<businessId, WASocket>`, so each business has its own live WebSocket connection.

Append-only log of every message (both directions).

| Column | Type | Notes |
|---|---|---|

| `businessId` | UUID | Foreign key → Business |

| `source` | String | `CUSTOMER` / `AI` / `RULE` / `SYSTEM` |

### `Contact`
One record per unique customer per business.

| Column | Type | Notes |
|---|---|---|

## 7. WhatsApp Service

**File:** `apps/backend/src/services/whatsapp.service.ts`

The `WhatsappService` class is a singleton-style service that manages all active Baileys socket connections.

### Key internals

```typescript
private sessions: Map<string, WASocket>   // live sockets keyed by businessId
private qrCodes: Map<string, string>       // temporary QR strings before connection
private aiService: AiService               // injected for message handling
```

### `connectBusiness(businessId)`

1. Loads auth state from `./sessions/business_<businessId>/` using Baileys `useMultiFileAuthState`.
2. Creates a `makeWASocket` instance with the loaded state.
3. Registers three event listeners:
   - `creds.update` — persists credentials to disk on every change
   - `connection.update` — handles QR generation, connection open/close, and DB session status updates
   - `messages.upsert` — the main message handler (see pipeline below)
4. Waits 2 seconds for the first QR to generate, then returns it.

### Reconnect logic

On `connection.update` with `connection === 'close'`:
- If the disconnect reason is **not** `loggedOut`, `connectBusiness` is called recursively to reconnect.
- If the reason is `loggedOut`, the session and QR are cleared from memory.

### `getQrCode(businessId)`

- Returns a cached QR if one is already in memory.
- Returns `'ALREADY_CONNECTED'` if the DB session shows `CONNECTED`.
- Otherwise calls `connectBusiness` to initiate a new connection.

## 8. AI Service

**File:** `apps/backend/src/services/ai.service.ts`

Supports five AI providers through a unified interface.

### Provider routing

| Provider value | SDK used | Base URL override |
|---|---|---|
| `anthropic` | `@anthropic-ai/sdk` | n/a |
| `openai` | `openai` | none (official) |
| `gemini` | `openai` | `https://generativelanguage.googleapis.com/v1beta/openai/` |
| `deepseek` | `openai` | `https://api.deepseek.com` |
| `openrouter` | `openai` | `https://openrouter.ai/api/v1` |

Gemini, DeepSeek, and OpenRouter use OpenAI-compatible APIs so they share the same client code.

### `handleIncomingMessage(businessId, remoteJid, messageText, isNewContact, sendMessageCb)`

Decision tree (in order of priority):

```
1. Fetch AiConfig for businessId
   → no config found? stop.

2. isNewContact AND greetingEnabled AND greetingMessage?
   → send greeting, stop.

3. config.isActive === false?
   → stop.

4. Check each rule in config.rules:
   → messageText.toLowerCase().includes(rule.keyword.toLowerCase())?
   → send rule.reply, stop.

5. config.prompt AND config.apiKey?
   → call AI provider with system prompt + user message
   → send AI reply.
```

## 9. Message Processing Pipeline

```
Customer sends WhatsApp message
          │
          ▼
Baileys socket emits messages.upsert
          │
          ├── Filter: skip messages from self (fromMe)
          ├── Filter: skip empty messages
          │
          ▼
Log incoming message → MessageLog (direction: INCOMING, source: CUSTOMER)
          │
          ▼
Check Contact table → upsert if new
          │
          ├── contact.isAiPaused === true? → STOP (human handles it)
          │
          ▼
AiService.handleIncomingMessage()
          │
          ├─ New contact + greeting on? → sendMessage(greeting) → log OUTGOING/RULE
          ├─ Keyword match?             → sendMessage(reply)    → log OUTGOING/RULE
          └─ AI active?                → callProvider()        → log OUTGOING/AI
```

## 10. Session Management

Baileys stores authentication credentials on disk:

```
./sessions/
  business_<uuid>/
    creds.json
    keys/
      ...
```

These files allow the platform to reconnect to WhatsApp without re-scanning a QR code on every server restart. The `Session` table in PostgreSQL tracks the current connection status (`CONNECTED` / `DISCONNECTED`) for display in the UI.

On server restart, active sessions are not automatically reconnected — a QR scan or manual reconnect is required.

## 11. Frontend Structure

The frontend is a Next.js 14 App Router application.

### Pages

| Route | File | Purpose |
|---|---|---|
| `/` | `app/page.tsx` | Login and sign-up form |
| `/dashboard` | `app/dashboard/page.tsx` | WhatsApp QR connection |
| `/dashboard/settings` | `app/dashboard/settings/page.tsx` | Automation configuration |
| `/dashboard/logs` | `app/dashboard/logs/page.tsx` | Inbox / live chat view |

### Navigation (Sidebar)

Defined in `app/dashboard/layout.tsx`. Three nav items: **Connect WhatsApp**, **Automation**, **Inbox**.

### Auth flow

- On load, `page.tsx` checks for a `profy_token` cookie.
- If found, redirects to `/dashboard`.
- Dashboard layout checks the same cookie on mount; if missing, redirects to `/`.
- Token is set with a 7-day expiry on login/signup.

### API client

`src/lib/api.ts` exports an Axios instance pre-configured with:
- `baseURL: http://localhost:3001/api`
- A request interceptor that reads `profy_token` from cookies and adds `Authorization: Bearer <token>` to every request.

### Polling

Both the dashboard and inbox pages use `setInterval` polling at 5-second intervals to refresh connection status and message logs without requiring WebSockets on the frontend.

## 13. Running the Project

### Prerequisites

- Node.js 18+
- pnpm
- PostgreSQL running locally or via Docker

### 1. Install dependencies

```bash
pnpm install
```

### 2. Set up the database

```bash
cd apps/backend
cp .env.example .env    # fill in DATABASE_URL and JWT_SECRET
npx prisma migrate dev
```

### 3. Start the backend

```bash
cd apps/backend
npx ts-node src/index.ts
# or with nodemon:
npx nodemon src/index.ts
```

### 4. Start the frontend

```bash
cd apps/frontend
pnpm dev
```

Frontend runs on `http://localhost:3000`, backend on `http://localhost:3001`.

### Docker Compose

```bash
docker compose up
```

## 14. Risks and Limitations

| Risk | Detail |
|---|---|
| **No official API** | Uses the WhatsApp Web protocol, which is not officially supported by Meta. Sessions can be disrupted by WhatsApp server changes. |
| **Session bans** | Sending messages too frequently or in bulk can trigger temporary or permanent bans on the linked number. |
| **Protocol changes** | Meta can update the WhatsApp Web protocol, breaking Baileys until a new version is released. |
| **Single-message AI context** | The current AI implementation sends only the current message as user input. It does not maintain conversation history across turns. |
| **In-memory sessions** | `WhatsappService` stores socket instances in a `Map`. If the backend process restarts, all active sockets are lost and QR re-scan is required. |
| **API key storage** | AI provider API keys are stored in plaintext in the `AiConfig` table. Encryption at rest should be added before production use. |
| **No rate limiting** | The backend has no rate limiting middleware. Endpoints are open to abuse without additional infrastructure. |
